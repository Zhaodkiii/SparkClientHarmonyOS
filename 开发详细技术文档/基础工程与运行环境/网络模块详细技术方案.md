# SupportClientHuawei 网络模块详细技术方案

## 1. 对标范围与结论

本文定义 `SupportClientHuawei` 的网络底座设计与 iOS 对标规则，并记录当前工程实现状态。功能基线来自 iOS [网络模块需求](../../../../SupportClient/总领文档/基础工程与运行环境/网络模块需求.md) 及其实际网络代码；HarmonyOS 复用同一后台接口契约，而非逐行翻译 Swift。

**当前实现状态（2026-07-18）：** 六阶段网络底座已在 `entry` 模块落地，代码位于 `entry/src/main/ets/` 的 `App/`、`Core/Networking/`、`Projects/Core/Networking/`、`Foundation/`；单元测试见 `entry/src/test/ets/Networking/NetworkModule.test.ets`。业务登录 UI、完整会话恢复与路由仍待后续模块接入；`SessionInvalidation` 已预留订阅点。

对标原则：

1. 路径、方法、查询参数、JSON 字段、包裹响应、错误码、Token 字段、ETag 语义必须与 iOS 一致。
2. 401 先刷新再重放一次、刷新单飞、非幂等请求不自动重试、缓存按账号隔离等可观察行为必须一致。
3. iOS 的 `URLSession`、actor、Keychain、`NWPathMonitor` 分别由 ArkTS 网络传输、Promise 单飞/队列、安全存储、Network Kit 实现；不要求 API 或代码逐字对应。
4. 文档和 iOS 代码冲突时，以实际代码与可执行测试为准；未知规则必须登记为待确认项。

结论：统一 API、HTTP、JSON、Token、401、重试、串行、请求合并、ETag、缓存、网络状态和脱敏日志均为必需对齐项，且已按本文目录在工程中实现。Token 经 `SecureTokenStore`（应用私有目录加密快照）隔离，禁止写入普通 Preferences。

## 3. 分层职责与请求链路

| 层 | 职责 | 禁止承担 |
| --- | --- | --- |
| `SupportBackend` | 组装 Engine、缓存、TokenProvider 与领域 API；唯一应用级入口 | UI 状态、页面跳转 |
| API | 相对路径、DTO、解码模式与请求策略 | Transport、页面状态 |
| Operation/Configuration | 业务用途日志、GET 合并、统一执行和解码 | ViewModel、路由 |
| Engine | URL、Header、Request ID、鉴权、401、ETag、重试、取消 | 业务字段解释 |
| Transport | 真实 HTTP 请求和原始响应转换 | Token、业务错误、UI |
| Cache/Security | 账号隔离元数据、ETag body、安全 Token | 页面展示逻辑 |

```text
API -> Operation -> BackendConfiguration -> CallbackCache
    -> SerialRequestGate -> NetworkEngine -> Auth / ETag / Retry
    -> Transport -> Response Decoder -> API result
```

## 4. 核心关键技术与实现方案

### 4.0 官方能力、依赖与落地前置条件

华为官方的[发送网络请求（ArkTS）](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/http-request)属于 Network Kit 的 HTTP 能力；用于创建 HTTP 会话、发起请求、取消请求和关闭会话。项目必须在 `module.json5` 申明网络访问权限，并且所有 HTTP 会话的创建、取消和销毁都只能由 `SupportNetworkTransport` 管理。不得让各页面分别创建会话。

官方的[Universal Keystore Kit ArkTS API](https://developer.huawei.com/consumer/cn/doc/harmonyos-references/universal-keystore-arkts)提供 `@ohos.security.huks` 密钥库能力；它是 `SecureTokenStore` 的密钥保护基础，而不是业务 API 直接调用的工具。官方文档中心还将 Network Kit、ArkData、HUKS、ArkTS 并发和 DevEco Testing 分列维护，开发前必须以项目目标 API Level 复核具体参数、权限、可用设备和弃用状态。

首期 `entry/src/main/module.json5` 需要增加网络权限；依赖策略如下：

| 能力 | 首选实现 | 允许的替代 | 不允许 |
| --- | --- | --- | --- |
| HTTP | `@ohos.net.http` 的薄封装 | `@ohos/axios` 藏在 Transport 内 | UI/API 层直接使用 axios/http |
| 网络状态 | `@kit.NetworkKit` 的 `connection` | 无 | 以一次请求失败永久判断无网 |
| 普通元数据 | `@kit.ArkData` Preferences | 应用私有 JSON 索引 | 用于 Token/STS Secret |
| 缓存 body | `context.filesDir` 应用私有文件 | 无 | 公共目录或跨账号目录 |
| 密钥与凭证保护 | HUKS + 加密 Token 快照 | 经安全评审的安全存储封装 | 明文 Preferences |

### 4.1 统一装配、环境和领域 API

#### 目标与边界

`SupportBackend.ets` 是唯一的组合根：创建 `Transport`、`NetworkEngine`、`DeviceCache`、`ETagStore`、`AuthTokenProvider`、`BackendConfiguration`，再暴露 `auth`、`otp`、`device`、`files`、`oss`、`ocr`、`aiConfig`、`accountIdentity`、`deactivation`。它对应 iOS `SupportBackend.swift`，其价值是让全部业务调用使用同一套 Token、缓存、日志与错误行为。

环境配置只存放 Base URL、环境名、默认超时、诊断开关；每个 API 只保留相对 path。Base URL 和 path 的拼接必须遵守：Base URL 尾部斜杠和 path 头部斜杠只保留一个；query 必须逐项编码和排序，不能用字符串拼接。

#### 核心代码骨架

```ts
export class SupportBackend {
  readonly configuration: SupportBackendConfiguration
  readonly auth: AuthAPI
  readonly otp: OTPAPI
  // device/files/oss/ocr/aiConfig/accountIdentity/deactivation 同样注入

  constructor(environment: BackendEnvironment, appContext: common.Context) {
    const cache = new DeviceCache(appContext)
    const tokenStore = new SecureTokenStore(appContext)
    const provider = new AuthTokenProvider(tokenStore)
    const engine = new SupportNetworkEngine(environment, new SupportNetworkTransport(), provider, cache)
    this.configuration = new SupportBackendConfiguration(engine, cache)
    this.auth = new AuthAPI(this.configuration)
    this.otp = new OTPAPI(this.configuration)
  }
}
```

**本段为伪代码，不可直接复制进 `.ets`。** 它只表达依赖方向；实际 ArkTS 的 Context、构造参数、Kit 枚举、异常类型和权限必须以目标 SDK 编译结果为准。用户要求直接实现时，需为每个请求 body 声明确切 class/interface，避免 TypeScript 的动态 `Record`/对象索引写法，并在 `assembleHap` 成功后才可标记“已实现”。页面只能从应用容器取得 `SupportBackend`，不得自行 `new SupportNetworkTransport()`。

#### 验收

- 更换开发/测试/生产 Base URL 后，任何 API 文件无修改。
- 同一应用进程内只存在一套 Backend、TokenProvider 和会话失效订阅。
- 任意页面不直接引用 `@ohos.net.http` 或 `@ohos/axios`。

### 4.2 HTTP Transport、请求构建、超时和取消

#### 实现规则

`SupportNetworkTransport` 只接收完整 URL、方法、Headers、body 和 timeout，返回原始 `statusCode`、headers、body bytes。它不识别 `code/msg/data`，也不能注入 Token。网络引擎负责把业务请求转换为 Transport 请求。

对官方 HTTP 用法的落地要求：创建会话后发起请求；将请求选项中的方法、header、extraData、连接/读取超时与本项目 Request 一一映射；在取消时调用官方取消能力；无论成功、失败、取消，均在 `finally` 关闭/销毁该次会话。若目标 SDK 的 API 使用 `request()`、`destroy()` 或不同名称，以官方当前版本为准，但这套资源生命周期不可省略。

```ts
export interface NetworkTransport {
  execute(request: RawHttpRequest, cancellation: CancellationToken): Promise<RawHttpResponse>
}

// 关键逻辑：代码为实现骨架，不直接复制 SDK 签名。
async execute(raw: RawHttpRequest, cancellation: CancellationToken): Promise<RawHttpResponse> {
  const session = this.createPlatformHttpSession()
  const cancel = () => session.cancel?.()
  cancellation.onCancel(cancel)
  const start = Date.now()
  try {
    const response = await session.request(raw.url, this.toPlatformOptions(raw))
    return this.toRawResponse(response, Date.now() - start)
  } catch (error) {
    throw SupportNetworkError.fromPlatformError(error, raw.requestId)
  } finally {
    cancellation.offCancel(cancel)
    session.destroy?.()
  }
}
```

#### 请求构建细节

1. 每次**真实发送**时生成 UUID 作为 `X-Request-ID`；重试沿用同一链路 ID，并额外记录 attempt 编号。
2. `body` 为 JSON 时统一 UTF-8 编码并添加 `Content-Type: application/json`；二进制/文件 body 必须由 API 显式指定 Content-Type。
3. 只有 `requiresAuth` 才允许追加 Authorization；公共 API 不得意外携带 Token。
4. 对 ETag 请求禁用“底层透明缓存代替业务缓存”的行为，确保 Engine 可以明确处理 304。
5. 取消错误统一映射为 `cancelled`，被取消后不得触发普通重试，也不得更新 UI 状态。

#### 示例工程对照

`LiveStreaming/commons/utils/src/main/ets/network/interceptor/CallServerInterceptor.ts` 展示了“终点拦截器”把 method、headers、params、body、connect/read timeout 映射给 `@ohos/axios` 的思路。可借鉴“HTTP 只在最后一层发送”的边界；不能照搬其 `MockAdapter.adapter`，真实项目必须删除该适配器。`@ohos/axios` 也不能成为 Support API 的公开类型。

### 4.3 请求模型、响应解码与统一错误

#### 请求策略

`SupportNetworkModels.ets` 必须定义 `NetworkRequest`、`NetworkStrategy`、`RetryConfig`、`NetworkResponse`、`SupportNetworkError`，使每个 API 都可声明：是否鉴权、是否启用 ETag、串行 key、优先级、是否幂等、重试规则和请求级超时。API 只“声明策略”，Engine 才“执行策略”。

#### 两种响应模式

```ts
type ResponseDecodingMode = 'backendWrapped' | 'direct'

interface BackendWrappedResponse<T> {
  code: number
  msg: string | Record<string, unknown>
  data: T
}
```

- 普通业务 API 采用 `backendWrapped`：先解 `{ code, msg, data }`；仅 `code === 0` 返回 `data`。
- Token 刷新等接口采用 `direct`：根对象直接解为目标 DTO，不能误取 `data`。
- `msg` 为对象时按 `detail`、`code`、可读字段提取诊断信息；UI 由 `BackendErrorLocalizer` 映射本地化提示，不能直接展示服务端原文。
- 解码失败必须保留请求路径、HTTP 状态、Request ID、脱敏 body 摘要；原始 body 不可直接打印。

```ts
decodeWrapped<T>(raw: RawHttpResponse): T {
  const envelope = parseJson<BackendWrappedResponse<T>>(raw.body)
  if (envelope.code !== 0) {
    throw SupportNetworkError.business(envelope.code, normalizeMessage(envelope.msg), raw)
  }
  return envelope.data
}
```

统一错误边界为 `transport | http | business | refreshFailed | cancelled | decoding | invalidResponse | unauthenticated`。页面只处理该错误边界，不处理系统 HTTP/axios 异常。

#### 示例工程对照

`LiveStreaming/.../JsonResponseInterceptor.ts` 可参考“发送前补 JSON Accept/Content-Type、响应后解析 JSON”的插入位置；但它把 `ArrayBuffer` 直接判为不支持，不能满足本项目文件、OSS、ETag body 等场景。项目 Decoder 必须支持原始 bytes 与 JSON 两种响应。

### 4.4 Token、安全存储和刷新单飞

#### 数据与安全边界

```ts
interface AuthTokens {
  accessToken: string
  refreshToken: string
  tokenType: string
  accessTokenExpiresAt: number
}
```

`AuthTokenProvider` 管理内存快照、JWT `exp` 判断、刷新 Promise 与安全持久化。`SecureTokenStore` 负责生成/获取 HUKS 加密密钥、加密 JSON 快照、写入应用私有位置、读取并解密、删除快照；前者不直接读写文件，后者不理解接口逻辑。

Token 具体实现方案：

1. 第一次登录成功后，从 access JWT payload 读取 `exp`；无法解析时使用服务端显式过期字段，二者皆无时作为待确认契约，禁止无期限复用。
2. 生成或获取当前应用专用的 HUKS 对称密钥别名；密钥不能写入日志或导出到普通文件。
3. 用该密钥加密完整 `AuthTokens` JSON，密文与必要的非秘密版本/nonce 元数据存入应用私有目录；不将 Token 放入 Preferences。
4. 每次鉴权请求前读取内存快照；临近过期时进入 `refreshIfNeeded()`。
5. `refreshIfNeeded()` 若已有 `refreshPromise`，直接 await；否则创建 Promise、执行刷新、完整替换内存与密文快照，并在 `finally` 将 `refreshPromise` 清空。

```ts
private refreshPromise?: Promise<AuthTokens>

refreshIfNeeded(force: boolean = false): Promise<AuthTokens> {
  if (!force && this.cached && !this.isNearExpiry(this.cached)) return Promise.resolve(this.cached)
  if (this.refreshPromise) return this.refreshPromise
  this.refreshPromise = this.refreshTokens()
    .then(async tokens => { this.cached = tokens; await this.store.save(tokens); return tokens })
    .finally(() => { this.refreshPromise = undefined })
  return this.refreshPromise
}
```

刷新失败分类：本地没有凭证为 `unauthenticated`；后端明确刷新 Token 无效为 `refreshFailed` 且可清理；网络超时/5xx 为临时失败，必须保留快照；响应不符合 DTO 为 `invalidResponse`，保留证据以便排查但不盲目登出。

#### 示例工程对照

`LiveStreaming/.../TokenHeaderInterceptor.ts` 说明 Header 注入应在调用链中集中完成；`TokenRefreshInterceptor.ts` 说明“一个请求只允许刷新并重放一次”的保护。它们不具备安全存储、并发单飞或精确失效分类，不能直接用作生产实现。项目需保留其 `request.tokenRefreshed` 的思想，但将它提升到 `NetworkEngine` 的最大重放次数控制。

### 4.5 401、会话失效和应用生命周期

#### 识别与状态机

仅在下列任一条件确定时将其识别为鉴权失效：HTTP 401、后端约定的 401xx 业务码、明确的 `token_not_valid`/`invalid_token`/`token_expired` 标记。网关 HTML、未知 JSON、网络断开不能触发登出。

```text
authenticated request
  -> 401 / token-invalid business error
  -> forceRefreshTokens()
  -> success: replay once -> normal decoder
  -> known-invalid refresh failure: invalidateOnce() -> signedOut
  -> temporary failure: return refreshFailed, preserve session
```

`SessionInvalidation` 必须有 `isInvalidating` 或等效去重状态。执行顺序：阻断后续使用旧 Token → 清 Token 密文 → 清账号 ETag/文件/设备相关缓存 → 更新 AppSessionStore 为 signedOut → 广播路由事件。每一步允许被重复调用且不崩溃。UIAbility 恢复或冷启动时只从 `AppSessionStore` 读取最终状态，不能在页面里直接依据 401 跳转。

### 4.6 重试、退避、串行门控与 GET 合并

#### RetryLayer

默认配置：首次请求外最多两次；可重试 HTTP 429、500、502、503、504 与超时、DNS、连接失败、连接中断、无网络。先解析 `Retry-After` 秒数或 HTTP 日期；无该 Header 时使用 iOS 对齐退避 `[0, 750ms, 3000ms]`。401 永远先走刷新流程。POST/PATCH/DELETE 仅在 API 显式 `isIdempotent=true` 时重试，上传和注销默认不能自动重发。

```ts
for (let attempt = 0; ; attempt++) {
  try { return await performAttempt(attempt) }
  catch (error) {
    if (!retryPolicy.shouldRetry(request, error, attempt) || cancellation.cancelled) throw error
    await delay(retryPolicy.delayFor(error, attempt))
  }
}
```

#### SerialRequestGate

对 `files.list`、OSS STS、OCR STS、同一设备登记等写入或时序敏感任务，使用稳定 `serialKey`。Gate 为每个 key 保存独立队列；队列项为 `{ priority, sequence, run, reject, cancellation }`。取队首时先比较 priority、再比较 sequence，实现同优先级 FIFO；不同 key 的队列没有共同锁，因此可并行。任务取消时从未执行队列移除；已执行时向 Transport 传播取消。

#### SupportCallbackCache

仅对 GET 生成 in-flight key，格式为 `GET + canonicalPath + sortedQuery + authScope`。首个调用保存 Promise，后续相同 key 直接 await；一定使用 `finally` 删除。它只解决“同时请求同一资源”，不能代替 ETag，也不能缓存修改请求。

### 4.7 ETag、文件缓存和账号隔离

`ETagStore` 保存 `etag`、`lastUpdated`、`expirationDate` 与响应 body。Key 为 `SHA-256(method + canonicalUrl + authFingerprint)`；`authFingerprint` 仅保存 hash，不能写明文 Authorization。目录建议为：

```text
<filesDir>/network-cache/<accountScope>/<hash>.body
<filesDir>/network-cache/<accountScope>/<hash>.meta.json
```

算法：请求前读取 meta，未过期则加 `If-None-Match`；收到 2xx + ETag 时先以临时文件写 body，再原子替换 body 与 meta；收到 304 时读取 body，验证存在和完整性后返回“已合并的 200 语义 response”；不存在、过期或读取失败则抛 `invalidResponse`。缓存有效期按 `no-store`、`max-age`、`Expires`、请求 TTL、默认 TTL 依次判定。

退出、账号切换、会话失效清除当前 `accountScope`；全局清理才可遍历所有命名空间。文件写入必须采用临时文件加原子移动，避免应用被杀时留下半个 JSON body。

### 4.8 网络状态、设备缓存与生命周期

`NetworkPathMonitor` 使用 `connection.createNetConnection()` 建立订阅，初始状态为 `unknown`，完成一次默认网络查询或收到首个事件后才设 `hasEvaluatedPath=true`。监听 `netAvailable`、`netLost`、`netUnavailable`，在 UIAbility/Application 生命周期中注册、解除注册和释放连接。网络状态只影响 UI 提示和启动门控；不得绕过 Engine 的重试、取消和 Token 规则。

`DeviceCache` 使用 Preferences 保存非敏感的用户 ID、设备 ID、上次登录账号、日志级别与缓存索引；所有 `put`/删除后必须 flush，并以 accountScope 做键前缀。不得存 access/refresh Token、STS Secret 或 API Key。示例 `PreferenceUtil.ts` 的 `getPreferencesSync`、`putSync`、`flush`、`clearSync` 是可参考的封装方式，但其日志会打印 value，项目实现必须删除该行为。

### 4.9 日志、脱敏与可测试性

`NetworkLogger` 必须记录 API/Operation、业务用途、method、脱敏路径、Request ID、requiresAuth、ETag、serialKey、优先级、attempt、状态码、响应字节数、耗时、缓存/合并状态。脱敏规则至少覆盖：`Authorization`、access/refresh token、password、code、API key、secret、STS、手机号和邮箱；body 仅可输出结构名、长度或字段白名单摘要。

`LiveStreaming/.../LoggerInterceptor.ts` 会打印 request headers、body 和完整 response，因此只能作为“计时与链式日志位置”参考，不能复制。生产实现必须先走 `NetworkLogSanitizer` 再调用 Logger。

测试通过可注入 `FakeTransport`、可控 Clock、可控 Delay 和临时文件目录完成，不依赖真实后台。单元测试至少覆盖：URL 拼接、包裹/直接解码、并发刷新单飞、401 仅重放一次、Retry-After、非幂等不重试、串行排序、GET 合并删除、304 合并、跨账号隔离、取消和日志脱敏。

## 5. 接口契约与数据模型

华为端使用 iOS 相同的 Base URL 环境、相对路径、HTTP 方法、请求/响应字段、业务码和 Token 规则；业务页面不得硬编码完整地址。

```ts
NetworkRequest {
  method: 'GET' | 'POST' | 'PUT' | 'PATCH' | 'DELETE'
  path: string
  query?: Record<string, string>
  headers?: Record<string, string>
  body?: object | ArrayBuffer
  timeoutMs?: number
  strategy: NetworkStrategy
}

NetworkStrategy {
  requiresAuth: boolean
  allowETag: boolean
  serialKey?: string
  isIdempotent: boolean
  queuePriority: 'veryHigh' | 'high' | 'normal' | 'low'
  retry: RetryConfig
  etagTtlMs?: number
}
```

普通接口使用包裹响应：

```json
{ "code": 0, "msg": "", "data": {} }
```

`code === 0` 返回 `data`，否则转换为业务错误；`msg` 兼容字符串和对象。Token 刷新等接口直接解析根对象，不套用 `data`。JSON 请求自动添加 `Content-Type: application/json`；原始字节与上传请求必须显式声明 Content-Type。

### 5.1 字段约定与 HarmonyOS DTO 规则

以下数据字典以 iOS 源码为事实来源，主要对应 `SupportAPIs.swift`、`API/Auth/*.swift`、`API/Account/*.swift`、`API/AI/AIConfigAPI.swift`。HarmonyOS DTO 必须使用后端 JSON 原字段名，不得根据 ArkTS 命名习惯私自改名：例如 `bundleId` 与 `bundle_id` 在不同接口中均真实存在。

| 约定 | 华为端实现要求 |
| --- | --- |
| 整数 ID | `userId`、`accountId`、`fileId` 等在 ArkTS 用 `number`；当前 iOS 使用 `Int64`，后端若未来可超过 JS 安全整数范围，必须改为 string 并与后端共同升级，不能静默截断。 |
| 可选字段 | 用 `field?: type` 接收；请求时只有 iOS `encodeIfPresent`/可选字段才允许省略，不能用空字符串替代 `undefined`。 |
| 命名转换 | 每个 DTO 显式写 JSON 字段名；禁止做全局 snake_case/camelCase 自动转换，以免 `bundleId`、`bundle_id` 混用。 |
| 日期 | 后端当前使用 ISO 8601 字符串或时间戳字符串；网络 DTO 原样保留 `string`，应用层再解析为 `Date`/毫秒。 |
| Secret | `password`、`identityToken`、`authorizationCode`、`deviceSecret`、`apiKey`、`accessKeySecret`、`securityToken` 都标为敏感字段，不进入日志、ETag、Preferences、错误提示。 |
| 响应包装 | 除“直接响应”已被后端确认的接口外，全部按 `{ code, msg, data }` 解包；下表响应字段均指 `data` 内字段。 |

#### HarmonyOS 通用模型

```ts
export interface BackendEnvelope<T> {
  code: number
  msg: string | Record<string, unknown>
  data: T
}

export interface AuthTokensDTO {
  accessToken: string
  refreshToken: string
  expiresIn: number      // 秒；落库前转换为 expiresAtMs
  tokenType: string      // 通常 Bearer
}

export interface AuthTokens {
  accessToken: string
  refreshToken: string
  expiresAtMs: number
  tokenType: string
}
```

`AuthTokensDTO` 是服务端传输模型，`AuthTokens` 是内存/安全存储模型；二者不能混用。`expiresAtMs = now + expiresIn * 1000`，并优先以 JWT `exp` 校正。若 iOS 与 JWT 的到期时间不一致，记录诊断并以更早过期时间为准。

| JSON 字段 | ArkTS 类型 | 必填 | 含义 |
| --- | --- | --- | --- |
| `userId` | number | 是 | 后端用户 ID。 |
| `accessToken` | string | 是 | 短期访问凭证。 |
| `refreshToken` | string | 是 | 刷新凭证。 |
| `expiresIn` | number | 是 | Token 剩余秒数。 |

### 5.3 OTPAPI：邮箱、手机号验证码

**iOS 事实来源：** `Projects/Core/Networking/API/Auth/OTPAPI.swift` 与 `DeactivationAPI.swift` 中的 `OTPRequestResponse`。

| 操作 | HTTP / Path | requiresAuth | 条件 |
| --- | --- | --- | --- |
| 邮箱发码 | `POST /api/v1/otp/email/request/` | `scene` 为 `identity_bind` / `identity_change` 时是 | 其他 scene 否 |

### 5.8 AccountIdentityAPI：身份列表、再认证、绑定和修改

**iOS 事实来源：** `API/Account/AccountIdentityAPI.swift`。

所有本模块接口都需要 Authorization。注意该模块的 JSON 使用 **snake_case**，与 Auth/OTP 的 `bundleId`、`deviceId` 不同，HarmonyOS DTO 必须逐接口实现。

| 操作 | HTTP / Path | 请求 / Query | 响应 |
| --- | --- | --- | --- |
| 身份列表 | `GET /api/v1/accounts/identities/` | query `bundle_id` | `IdentityListResult` |
| 请求再认证 | `POST /api/v1/accounts/identity-verification/request/` | `IdentityVerificationRequest` | `VerificationRequestResult` |
| 校验并签发 ticket | `POST /api/v1/accounts/identity-verification/verify/` | `IdentityVerificationVerifyRequest` | `VerificationTicketResult` |
| 绑定身份 | `POST /api/v1/accounts/identities/bind/` | `BindIdentityRequest` | `IdentityListResult` |
| 修改身份 | `POST /api/v1/accounts/identities/change/` | `ChangeIdentityRequest` | `IdentityListResult` |

身份列表响应：`accountId: number`、`bundleId: string`、`identityScope: string`、`identities: IdentityStatusDTO[]`；每一身份为 `provider: string`、`bound: boolean`、`maskedValue: string`、`modifiable: boolean`、`bindable: boolean`。当前已知 provider 为 `phone`、`email`、`apple`；华为端对 `apple` 只能展示已绑定状态，不得承诺可在 HarmonyOS 内发起 Apple 认证。

| 请求 DTO 字段 | JSON 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- | --- |
| `IdentityVerificationRequest.provider` | `provider` | string | 是 | `phone` / `email` / `apple`。 |
| `purpose` | `purpose` | string | 是 | 绑定/换绑流程用途，如 `bind_identity`、`change_identity`。 |
| `bundleId` / `deviceId` | `bundle_id` / `device_id` | string | 是 | 注意 snake_case。 |
| 认证 phone/email proof | `otp_id`、`code` | string | 是 | 通过 OTP 完成；code 敏感。 |
| 认证 apple proof | `identity_token`、`authorization_code?`、`user_identifier` | string | 条件必填 | 仅 Apple 流程；敏感。 |
| `BindIdentityRequest.verificationTicket` | `verification_ticket` | string | 是 | 再认证签发的短期 ticket，敏感。 |
| phone/email bind proof | `target`、`otp_id`、`code` | string | 是 | `target` 为待绑定的新号码/邮箱。 |
| `ChangeIdentityRequest.newTarget` | `new_target` | string | 是 | 新手机号/邮箱。 |
| `newOtpId` / `newCode` | `new_otp_id` / `new_code` | string | 是 | 新目标 OTP；code 敏感。 |

`VerificationRequestResult`：`otpId?: string`、`expiresIn?: number`、`provider?: string`、`ready?: boolean`。Apple 路径可用 `ready=true` 而无 otpId；phone/email 必须有 otpId。`VerificationTicketResult`：`verificationTicket: string`、`expiresIn: number`，ticket 不得写 Preferences。绑定/修改成功都返回完整 `IdentityListResult`，应整体刷新本地身份 UI，不要仅乐观修改单行。

### 5.9 DeactivationAPI：账号注销提交

**iOS 事实来源：** `API/Account/DeactivationAPI.swift`。

操作：`POST /api/v1/deactivation/`，requiresAuth=true，非幂等，默认不自动重试。用户重复点击必须由 UI 禁用/提交状态防抖；网络未知时不可盲目二次提交。

| 请求字段 | JSON 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- | --- |
| `reason` | `reason` | string | 否 | 用户注销原因。 |
| `immediateDeactivation` | 同名 | boolean | 是 | 是否立即注销。 |
| `countdownHours` | 同名 | number | 否 | 延迟注销时的倒计时小时。 |
| `dataRetentionDays` | 同名 | number | 是 | 数据保留天数。 |
| `anonymizePersonalData` | 同名 | boolean | 是 | 是否匿名化个人数据。 |
| `deleteRelatedData` | 同名 | boolean | 是 | 是否删除关联数据。 |
| `verification` | `verification` | object | 否 | 身份验证载荷；后端何时强制必填待确认。 |

`verification` 子字段：`type: string` 必填、`identityToken?: string`、`authorizationCode?: string`、`userIdentifier?: string`、`otpId?: string`、`code?: string`。Apple 分支使用 identityToken/authorizationCode/userIdentifier；OTP 分支使用 otpId/code；均为敏感字段。

响应 `AccountDeactivationSubmissionResponse`：`deactivationId: number` 必填、`state: string` 必填、`scheduledAt?: string`、`immediateDeactivation?: boolean`、`countdownHours?: number`。响应成功不代表立即清空本地会话的最终时机：应以产品规则决定“提交后登出”还是“到期后登出”，该规则目前待产品确认。

## 8. 实施拆分与验收

| 阶段 | 交付 | 完成标准 | 状态 |
| --- | --- | --- | --- |
| 1 | 环境、请求/响应/错误、Transport、Backend | GET/POST 可发送，Request ID 可关联日志 | 已完成 |
| 2 | Decoder、领域 API DTO | 与 iOS 同样本得到相同业务结果 | 已完成 |
| 3 | 安全 Token、会话恢复、刷新单飞、401 | 并发只刷新一次，失效只登出一次 | 已完成 |
| 4 | Retry、Serial Gate、GET 合并、取消 | 策略符合幂等性、排队和合并要求 | 已完成 |
| 5 | ETag、账号隔离缓存、网络监听 | 304 可恢复，切账号不串缓存 | 已完成 |
| 6 | 脱敏日志、Mock Transport、单测 | 覆盖全部关键异常场景 | 已完成 |
| 7 | ArkTS 编译门、权限与资源引用 | API 24 `assembleHap` 错误数为 0；权限声明与 reason 资源齐全 | 已完成（2026-07-18） |

必须通过以下验收：

1. Base URL 与相对 path 的各种斜杠组合正确。
2. 包裹响应、非零业务码、对象型 `msg`、直接 Token 响应均正确解析。
3. 鉴权接口自动带 Token，公共接口不带 Token。
4. 十个并发鉴权请求只发出一次刷新请求。
5. 401 刷新成功仅重放一次；Refresh Token 失效只触发一次会话失效。
6. 429/5xx/网络异常按规则退避；非幂等 POST 不自动重发。
7. 同 `serialKey` 串行、不同 key 并行；取消请求不更新业务状态。
8. 相同 GET 并发只发一个请求，结束后一定删除 in-flight 状态。
9. ETag 首次保存、后续携带、304 合并成功；无 body 的 304 必须报错。
10. 账号缓存完全隔离；登出、切换、失效清理可重复调用。
11. 日志中不得出现 Token、API Key、STS Secret 或完整敏感 body。
12. 离线、首次未评估、网络恢复均不导致重复登录、设备登记或路由。
13. **编译门：** 在工程根目录执行目标 DevEco Studio 附带 Node/Hvigor 的 `assembleHap`；必须得到 `BUILD SUCCESSFUL`。本次验证产物为 `entry/build/default/outputs/default/entry-default-unsigned.hap`。

> 编译通过只说明 ArkTS/资源/权限可构建，不等于已完成真实 SparkService 联调、HUKS 密钥存储替换、设备安装或十项接口验收。未联调的接口不得仅凭文档或 DTO 标为“已验证对齐”。

## 9. 风险与待确认项

| 风险 | 处理要求 |
| --- | --- |
| 示例 MockAdapter 未移除 | 生产 Transport 禁止接入 Mock Adapter |
| 原始 Header/body 日志 | 上线前必须接入 `LogSanitizer` |
| Preferences 存 Token | 一律改为 `SecureTokenStore` |
| API 直接依赖 Axios | 限制在 Transport 内部 |
| 无刷新单飞 | 列为强制验收项 |
| 无账号命名空间缓存 | key 必含账号/鉴权指纹 |
| 304 无本地 body | 返回 `invalidResponse` |
| 将文档伪代码直接复制为 ArkTS | 先补明确 DTO、异常类型、权限与 SDK 编译验证；未通过 `assembleHap` 不得标记实现完成 |
| `SupportAPIs.ets` 的 Device/File/OSS/OCR 聚合类型 | 当前仅提供可编译组合根类型；逐接口实现必须以 SparkService 的 route/serializer/service/test 完成字段映射和联调后再交付 |

上线开发前必须向后端/产品确认：

1. 开发、测试、生产 Base URL 与证书策略，以及是否允许调试环境 HTTP。
2. 全部 API 路径、字段、字段别名、成功/业务错误码、直接或包裹响应模式。
3. Refresh Token 失效的状态码、业务码、消息标志，以及临时不可用的判定方式。
4. 各写操作的幂等性、幂等键支持情况与可重试范围。
5. ETag 覆盖接口、Cache-Control/Expires 规则、ETag 是否按用户隔离。
6. OSS/OCR STS 有效期、刷新阈值、端侧直传要求与密钥日志红线。
7. 华为端目标 SDK/API Level 及最终的 HTTP、安全存储实现选择。
